## 2. Аргументація архітектурних рішень

Повна аргументація — `docs/pinout.md`; ключові рішення з посиланнями:

| Питання | Рішення | Підстава |
|---|---|---|
| Чому I²C для IMU і OLED, одна шина | обидва пристрої мають лише I²C (у модулях GY-521 і 0.96" OLED), адреси не конфліктують (0x68 / 0x3C) | RM-MPU §4.32; SSD §8.1.5; скан ЛР1 — рівно 2 ACK |
| Чому PB8/PB9 | AF6 = I2C1 (DS «Port B AF mapping»); Arduino D15/D14 | DS; UM2953 «ARDUINO connectors» |
| Чому 100 кГц, а не 400 | перевірено записом ЛР1 (100.00 кГц); бюджет шини 32 % при 200 Гц опитування; Fm розраховано і готове (`BOARD_I2C_TIMING_400K`) для ЛР3 | `pinout.md` §4 |
| Чому SCK на PA1 | PA5 зайнятий LD4 | UM2953 «LEDs» — потрібні **усі три** документи: DS (AF0 на PA1), RM (SPI1 тактується від PCLK, BR), UM (PA5 = LED) |
| Чому програмний CS# на PB0 | апаратний NSS знімається між кадрами в master-режимі; транзакція SD — під одним CS# | RM0490 «SPI: NSS management»; контрольне питання 6 |
| Чому SPI 375 кГц → 6 МГц | SD init ≤ 400 кГц (SD Spec 6.4.1); 6 МГц — запас під макетку | RM: f<sub>SPI</sub> = PCLK / 2<sup>BR+1</sup> |
| Чому обидва серво на TIM3 | один таймер, дві однакові частоти 50 Гц → спільні PSC/ARR не обмеження; вільні таймери лишаються для ЛР3 | RM «TIM3»; AN4776 |
| Чому окреме живлення серво | stall 2 × 650 мА > можливостей USB/3V3; кидки струму скидають МК | `pinout.md` §3 |
| Конфлікт камери | у C031 немає DCMI, порти A/B не мають 8 вільних підряд пінів, 12 КБ RAM < кадру QQVGA → камера на цій платформі нереалізовна; аналіз для F446 | `pinout.md` §5.1 |
| Чому STOP+START, а не repeated START | так WHO_AM_I читався в ЛР1 і це видно в записі; Sr — окремий режим `cap rs` для перевірки | `analysis.md` §1.1, §1.4 |

## 4. Аналіз записів логічного аналізатора

Детально — `docs/captures/analysis.md` (по підрозділу на інтерфейс), процедура запису і параметри —
`docs/captures/README.md`. Коротко за записом ЛР1 (`lr1_bringup_all.vcd`):

| Інтерфейс | Що побачено | Розраховано | Виміряно |
|---|---|---|---|
| I²C | `S 68W+ 75+ P` · `S 68R+ 68- P` — WHO_AM_I = 0x68; ручне декодування збігається з sigrok | f<sub>SCL</sub> 100 кГц; t<sub>LOW</sub>/t<sub>HIGH</sub> 5.875/3.94 мкс | 100.00 кГц; 5.0/5.0 мкс (А-3) |
| SPI | 80 тактів, mode 0 | 375 кГц | 373.8 кГц; між байтами +2 мкс (HAL) |
| UART | 18 рядків лога розкодовано з лінії TX | 8.6875 мкс/біт | 8.675 мкс |
| PWM | 226 імпульсів | 1500 / 20 000 мкс | 1500.0 / 20 000.0 мкс; перший 1507.2 (А-6) |

Аномалії: А-1 нульові глітчі SDA у VCD Wokwi; **А-2 HAL повертає через 5.9 мс те, що на шині
закінчилося за 105 мкс** (розбіжність «HAL ↔ шина»); А-3 ідеальний меандр SCL; А-4 CS# = 0 до
ініціалізації; А-5 сміттєвий символ UART на старті; А-6 подовжений перший імпульс PWM;
А-7 свідома: NACK на 0x69.

⏳ Для записів ЛР2 в `analysis.md` уже наведено очікувані послідовності байтів (у т. ч. всі кадри SD
з пораховими CRC7) і таблиці «розраховано / виміряно» для заповнення; скриншоти PulseView —
у `docs/lab_2/img/`.

## 5. Структура проєкту і бібліотеки

`docs/architecture.md`: шари `Core / Drivers / Interfaces / Platform / Devices / App`, таблиця дозволених
залежностей, як драйвер бачить шину (`bus_i2c_t`, `bus_spi_t`), де живе знання про плату (`board.h`),
обмеження секцій USER CODE CubeMX, **component diagram** (Mermaid, рендериться на GitHub).

* **Правило залежностей перевіряється автоматично** двома незалежними способами: `tools/check_deps.py`
  (111 `#include` у 36 файлах, 0 порушень; плюс пошук HAL-ідентифікаторів поза Platform) і компіляцією
  Devices/App хостовим gcc без заголовків HAL. Перевіряльник має власні тести на 4 види порушень —
  саме вони знайшли П-7.
* **HAL**: увімкнено 11 модулів, кожен з коментарем «навіщо» у `stm32c0xx_hal_conf.h`; EXTI і PWR
  вимкнено, DMA — лише заголовок (П-4); у збірку йдуть 14 .c-файлів HAL проти 22 у ЛР1.
* **Попередження**: власний код — `-Wall -Wextra -Wshadow -Wundef -Wstrict-prototypes -Werror`;
  вендорський — `-Wall -Wextra` (0 попереджень), суворіші прапорці — лише для свого коду (П-2).
* **Версії**: HAL 1.4.1, CMSIS Device 1.4.1, CMSIS-Core 6.1, Unity 2.6.0 (sha256), тулчейн — Docker
  на Ubuntu 22.04, `make versions` у CI (`docs/third_party.md`).

## 7. Журнал проблем

| # | Симптом | Root cause | Виправлення | Коміт |
|---|---|---|---|---|
| П-1 | Власний декодер I²C показував `STOP START` посеред байта у записі Wokwi, а PulseView — ні | Wokwi пише кілька змін одного сигналу з **однаковою міткою часу** (відпускання ACK: `SDA 1, SCL 0, SDA 0` в одну нс); обробка подій по одній дає «глітч» нульової тривалості при SCL = 1 | Події згортаються по мітці часу (`vcdtool.snapshots`); синтетичний тест з такими глітчами | `7115589`, тест `a3d2d99` |
| П-2 | Із суворішими прапорцями (`-Wundef -Wstrict-prototypes`) збірка HAL дає 49 попереджень (48 у `stm32c0xx_hal_spi.c`, 1 у `syscalls.c`); з `-Werror` — не збирається | Вендорський код не писався під ці прапорці | Окремі `CFLAGS` для власних і вендорських об'єктів: власний код — суворі + `-Werror`, HAL — `-Wall -Wextra` (0 попереджень), нічого не придушено «глобально» | `758c2b2` |

## 10. Відповіді на контрольні питання

**1. Datasheet МК vs reference manual vs user manual.** Datasheet (DS13867) — що є в конкретному
кристалі й корпусі: розпіновка, таблиці AF, електричні характеристики (FT-піни, струми). Reference
manual (RM0490) — як працює периферійний блок: регістри, тактування, формули (TIMINGR, BR, BRR).
User manual плати (UM2953) — що з цього виведено на роз'єми і що вже зайнято (LED, кнопка, VCP,
solder bridges). Рішення, для якого знадобились усі три — **SPI1_SCK на PA1**: DS — PA1 і PA5 обидва
мають AF0 = SPI1_SCK у LQFP48; RM — SPI1 тактується від PCLK, BR = /128 дає 375 кГц; UM — PA5 зайнятий
LD4, тому PA5 відхилено.

**2. Чому I²C — open-drain.** На шині кілька пристроїв, і кожен може тягнути лінію до 0 (ACK, clock
stretching, арбітраж); «1» — це відпущена лінія, яку піднімає pull-up (wired-AND). У push-pull, якщо
майстер виставляє 1, а slave тягне 0 для ACK, — пряме КЗ між виходами: великий струм, на аналізаторі —
проміжний рівень/«сходинка» або лінія, що не опускається під час ACK (декодер покаже NACK), а при
арбітражі двох майстрів — спотворені біти. Вихідні каскади можуть вийти з ладу.

**3. Від чого залежить номінал pull-up.** Знизу — від струму стоку I<sub>OL</sub> (3 мА для Sm/Fm):
R<sub>min</sub> = (V<sub>DD</sub> − V<sub>OL</sub>)/I<sub>OL</sub> ≈ 0.97 кОм при 3.3 В. Зверху — від часу наростання
t<sub>r</sub> і ємності шини: R<sub>max</sub> = t<sub>r</sub>/(0.8473·C<sub>b</sub>) ≈ 23.6 кОм (Sm, 50 пФ), 7.1 кОм (Fm).
Кілька модулів з власними pull-up з'єднуються паралельно: еквівалентний опір падає (у нас 4.7‖4.7‖~40 ≈
2.2 кОм — нормально); з 4–5 модулями можна опуститися нижче R<sub>min</sub> — лінія не опускається до V<sub>OL</sub>,
тоді зайві резистори випаюють (`pinout.md` §4).

**4. SCCB vs I²C.** SCCB (OmniVision) — підмножина I²C: 9-й біт після байта — «don't care» (камера не
зобов'язана давати ACK), немає повторного START при читанні (запис адреси регістра і читання — окремі
транзакції з STOP), немає clock stretching. Стандартний HAL I²C трактує відсутність ACK як помилку:
`HAL_I2C_Master_Transmit` повертає `HAL_ERROR` з `HAL_I2C_ERROR_AF`, хоча камера команду прийняла;
`HAL_I2C_Mem_Read` використовує Sr, якого SCCB не вимагає підтримувати. Тому для SCCB або ігнорують AF,
або читають двома транзакціями — так, як наша прошивка вже читає MPU-6050 за замовчуванням.

**5. CPOL і CPHA.** CPOL — рівень SCK у спокої (0 — низький); CPHA — на якому фронті захоплюються дані
(0 — на першому, 1 — на другому). microSD у SPI-режимі працює в **mode 0** (CPOL = 0, CPHA = 0: дані
змінюються на спаді, захоплюються на фронті). Підтверджено на записі ЛР1: SCK у спокої = 0
(`analysis.md` §2.1); декодер sigrok у mode 0 видає `FF`, а при CPHA = 1 зсунув би біти. ⏳ для кадрів
CMD0/CMD8 запису `cap spi`: R1 = `01` і echo `AA` декодуються лише в mode 0.

**6. Чому програмний CS#.** Транзакція SD/flash — це команда + адреса + (очікування) + дані + (busy), і
CS# має триматися низьким увесь цей час, а між транзакціями — підніматися (для W25Q фронт CS# **запускає**
програмування). Апаратний NSS у master-режимі STM32 керується блоком SPI (знімається при вимкненні SPI
або між кадрами в NSSP-режимі) і не знає меж транзакції. До того ж на одній шині кілька slave → потрібно
кілька CS#, а апаратний NSS — один. GPIO дає повний контроль; ціна — ~22 мкс між CS#↓ і першим тактом
(видно на записі).

**7. Мінімальна частота дискретизації.** Для надійного декодування — щонайменше **4×** частоти шини
(краще 8–10×), щоб надійно побачити кожен рівень між фронтами і фазу даних відносно тактів:
I²C 100 кГц → ≥ 0.4–1 МГц; SPI 375 кГц / 6 МГц → ≥ 1.5 / 24 МГц; UART 115200 → ≥ 0.5–1 МГц (декодер
бере середину біта); PWM 50 Гц з роздільністю 1 мкс → 1 МГц. FX2-аналізатор (fx2lafw) обмежений
24 МГц (USB 2.0 HS і буфер FX2) — SPI 6 МГц на межі, піксельна шина камери — ні (`analysis.md` §6). У
Wokwi — 1 ГГц за форматом, фактичний крок міток 25 нс.

**8. Вплив частоти APB.** I²C, SPI, USART і таймери тактуються від PCLK (на C0 — один APB): I²C —
TIMINGR рахується від I2CCLK = PCLK; SPI — f = PCLK/2<sup>BR+1</sup> (лише степені 2 → 375 кГц, 6 МГц, 12 МГц);
USART — BRR = PCLK/baud, похибка залежить від подільності; таймери — f<sub>TIM</sub> = PCLK (×2, якщо APB-дільник ≠ 1).
Розрахунок для USART2: BRR = 48 000 000 / 115 200 = 416.67 → 417 → 115 108 Бд, похибка −0.08 %; якби
PCLK = 24 МГц, BRR = 208.3 → 208 → 115 385 Бд (+0.16 %). Для TIM3: PSC = 48 − 1 дає рівно 1 мкс лише тому,
що PCLK = 48 МГц; зміна дерева тактування без зміни PSC зламала б серво (`pinout.md` §4).

**9. Чому серво не від 3V3 Nucleo.** SG90 розрахований на 4.8–6 В (від 3.3 В — слабкий момент і
нестабільність); струм у русі сотні мА, stall ~650 мА, а 3V3 LDO живить МК і сенсори — просідання
скидає МК (BOR), дає шум в АЦП і на I²C, LDO перегрівається. Двигун — індуктивне навантаження з кидками
струму.

**10. Спільна земля.** Сигнал PWM — напруга відносно землі МК; якщо GND джерела серво не з'єднаний з GND
МК, у серво немає опорного рівня для сигналу — струм керування шукає шлях через захисні діоди, рівні
«плавають», серво смикається. Те саме для логічного аналізатора: без спільної GND він вимірює різницю
потенціалів через ємнісні наводки — «щось видно», але рівні й фронти неправильні.

**11. Шари і що гарантує правило.** `Interfaces ← Devices ← App`, `Interfaces ← Platform → HAL`, `Core →
усе` (`architecture.md` §2). Гарантують: `tools/check_deps.py` у `make build` і CI (include-и між шарами
+ HAL-ідентифікатори поза Platform), сам перевіряльник покритий тестами; і компілятор — Devices/App
збираються на хості без HAL.

**12. Як драйвер отримує шину; як він працює в тесті.** Через вказівник на `bus_i2c_t`/`bus_spi_t` (таблиця
функцій + `ctx`), переданий у `mpu6050_setup(&dev, bus, addr)`. На STM32 це `board_i2c1` (обгортка HAL),
у тесті — `mock_i2c_bus`/`fake_mpu_bus`/`stub_i2c_bus`; код драйвера — той самий файл
`Devices/mpu6050.c`, зібраний звичайним gcc.

**13. Fake vs mock; приклад, де потрібен mock.** Fake — робоча спрощена реалізація (наш `fake_mpu6050` —
регістровий файл з автоінкрементом і станом SLEEP); тест перевіряє **результат**. Mock — об'єкт з
заданими **очікуваннями взаємодії**; тест перевіряє, що виклики були саме такі й у такому порядку.
Mock потрібен у `test_init_wakes_chip_first_then_configures`: справжній MPU-6050 після POR спить, і
важливо, щоб **першим** був запис `PWR_MGMT_1 = 0x01`; fake прийняв би конфігурацію в будь-якому
порядку і тест пройшов би з неправильним драйвером. Аналогічно для W25Q: «WREN перед Page Program»
перевіряється журналом SPI.

**14. Що свідомо не покриваємо тестами.** `Core/` (згенерований CubeMX код ініціалізації) і `Platform/`
(тонкі обгортки над HAL): їхня поведінка визначається HAL і залізом, мокати HAL означало б тестувати
власні припущення про HAL. Їх перевіряють на цілі: self-test і сценарії Wokwi, записи аналізатора
(саме так знайдено П-9, якого жоден хостовий тест не показав би). Вендорський HAL не тестуємо.
