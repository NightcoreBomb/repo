# Журнал проблем ЛР4 (П-22 …)

Продовження нумерації журналу ЛР2–ЛР3 (П-1 … П-21). Позначка **[ОС]** — проблема, якої немає
в super loop і яка виникла саме через ОС.

### П-22 [ОС]. Зависання ініціалізації: перша критична секція до старту планувальника
**Симптом.** Після додавання FreeRTOS прошивка зависала на `CHK …`: `HAL_Delay` в ініціалізації
пристроїв не повертався.
**Причина.** `xSemaphoreCreateMutex()`/`xQueueCreate()` входять у критичну секцію. До
`vTaskStartScheduler()` лічильник вкладеності `ulCriticalNesting` = 0xAAAAAAAA, тож вихід із секції
не вмикає переривання знову (так задумано в порті: щоб тік не прийшов до старту). SysTick
зупиняється → `HAL_Delay` чекає вічно.
**Виправлення.** Об'єкти ОС створюються в `app_rtos_start()` — після `app_start()`, тобто після
всіх `HAL_Delay`. `uwTickFreq` перемикається на `1000/TICK_HZ` там само (інакше `HAL_Delay` у
`app_start` «прискорювався» б у 10 разів при TICK_HZ=100). Коментар — `App/app.c` (`app_os_objects`).
**Як знайти швидше.** Пам'ятати, що «до старту планувальника — без API ядра», або перевіряти
PRIMASK у місці зависання.

### П-23. Прошивка з ядром не вміщується у Flash (+6.6 КБ)
**Симптом.** `region FLASH overflowed by 6684 bytes`.
**Причина.** Ядро (tasks.c 4.4 КБ, queue.c 1.65 КБ, heap_4 0.7 КБ, порт 0.6 КБ) поверх 24 КБ ЛР3.
**Виправлення.** `-flto` (прибирає дублікати й вбудовує дрібні функції між файлами); `tasks`
обходить власний реєстр замість `uxTaskGetSystemState` (`configUSE_TRACE_FACILITY 0`); власний
`parse_long` замість `strtol` (−0.6 КБ); без 64-бітного ділення; тести ОС (`os …`) і selftest
розведено по різних збірках (`OSTEST=1`); `_Min_Heap_Size = 0`. Підсумок: 31.5 КБ (96 %).

### П-24. LTO ламає асемблер порту
**Симптом.** `portasm.c: Error: invalid offset, value too big` на етапі LTO-лінкування.
**Причина.** Naked-функції порту з літеральними пулами (`ldr r2, =pxCurrentTCB`) після LTO
розміщуються далеко від своїх пулів (Thumb-1: ±1 КБ).
**Виправлення.** `port.o` і `portasm.o` компілюються без LTO (`Makefile`).

### П-25 [ОС]. Запас стека задачі `telem` — 44 Б
**Симптом.** Перший запуск у Wokwi: `tasks` → `telem … stack=352 stack_free_min=44`.
**Причина.** Статична оцінка (`tools/stack_tree.py`) зроблена на збірці без LTO, а кадр
перемикання контексту в порті ARM_CM0 V11 — 32 Б (апаратний) + 36 Б (LR + r4–r11), а не 64 Б.
Шлях `plat_log → os_uart_lock → xQueueSemaphoreTake → успадкування пріоритету` глибший за
`plat_log → plat_vfmt`, який врахувала оцінка.
**Виправлення.** `telem` 88 → 120 слів, `oled` 152 → 168, `imu` 124 → 140; heap 5632 → 5888 Б
(`OSTEST`: 6656 → 6912, кільце `trace` 48 → 32). Висновок для методики: статична оцінка — лише
нижня межа; остаточно розмір задає high water mark після найгіршого сценарію з запасом ≥ 25 %.

### П-26 [ОС]. Подвійне читання спільної змінної між задачами (`telem_ms`)
**Симптом.** Знайдено переглядом коду після П-27: `os_delay_until(&last, ms_ticks(a->telem_ms ?
a->telem_ms : 100))` читає `telem_ms` двічі. Якщо `cmd` (пріоритет 3) витісняє `telem` (2) між
читаннями й записує 0, `vTaskDelayUntil` отримує приріст 0 тіків → `configASSERT(xTimeIncrement > 0)`.
**Причина.** У super loop команда і телеметрія ніколи не перемежовувались — гонки не існувало.
**Виправлення.** Одне читання в локальну змінну.

### П-27 [ОС]. Рідкісний збій: `FATAL assert tasks.c:6790` / задача `imu` «готова», але не виконується
**Симптом.** Ручні запуски у веб-Wokwi (2 з 4 сесій, у перші 25 с): (а) після кількох команд —
`FATAL assert Middlewares/FreeRTOS/Source/tasks.c:6790` (`vTaskPriorityDisinheritAfterTimeout`:
`configASSERT(pxTCB->uxMutexesHeld)`); (б) в іншій сесії `imu` перестала виконуватись (`state=r`,
`run_us` не росте, `JIT n=0`), а `oled`/IDLE нижчого пріоритету працювали.
**Аналіз.** Обидва симптоми — неузгоджений стан ядра (TCB / списки). Перевірено й відкинуто:
API не-ISR з переривань (немає), пріоритети NVIC (на ARMv6-M критична секція = PRIMASK, усі
переривання), naked-обробники порту (дизасемблер), переповнення буферів (`getline`, рендер OLED,
формат). Найімовірніша причина — тонкий стек `telem` (П-25): `telem` стоїть у heap одразу над TCB
задачі `cmd`, а TCB `cmd` зв'язаний у списку затримок разом з `imu`; переповнення, що «перескочило»
нетронуті байти неініціалізованого локального масиву, high water mark не показує.
**Виправлення.** П-25 (запаси стеків), П-26, а також прибрано єдиний таймаут на м'ютексі
(`lk_take`: 50 мс → без тайм-ауту): час утримання шини обмежений однією транзакцією, а шлях
`vTaskPriorityDisinheritAfterTimeout` більше не використовується. Assert тепер друкує й ім'я
задачі. **Перевірка:** прогін «soak» у веб-Wokwi — команди кожні 0.4–1.5 с часу симуляції
(`stats`, `tasks`, `telem 0/20/100`, `mode rec/play/live`, `dump`, `hist`); результат — у звіті.
