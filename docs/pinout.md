### 1.1. Чому саме цей пін, а не сусідній

* **PA2/PA3** — не вибір, а факт плати: лише вони заведені на ST-LINK VCP (UM). Будь-який
  інший UART не дав би логу «з коробки» ні на Nucleo, ні в Serial Monitor Wokwi.
* **PB8/PB9** — у C031 I2C1 можна вивести на PB6/PB7, PB8/PB9 або PA9/PA10 (усі AF6, DS).
  PB8/PB9 — це Arduino D15/D14 (SCL/SDA), куди модулі з Arduino-роз'ємом підключаються
  без перехідників; PB6/PB7 лишаємо під USART1 (D1/D0) для можливого другого каналу,
  PA9/PA10 — під EXTI/таймери (див. «Відхилені варіанти»).
* **PA1 (SCK)** замість «стандартного» Arduino D13 = **PA5**: на PA5 сидить LD4 (UM «LEDs»),
  що навантажує лінію і блимає з частотою SCK. PA1 має ту саму AF0 = SPI1_SCK.
* **PA6/PA7** — MISO/MOSI SPI1 на D12/D11, стандартні Arduino-позиції; альтернативи для SPI1 у
  LQFP48 (PB4/PB5) зайняті таймером серво.
* **PB0 (CS#)** — довільний GPIO; D10 — Arduino-конвенція для SS. Апаратний NSS (PA4/PA15) не
  використовуємо: у режимі master STM32 знімає NSS між кадрами, а транзакція SD (команда +
  відповідь + дані) має йти під одним CS# (див. звіт, контрольне питання 6).
* **PA0** — ADC1_IN0, Arduino A0; на PA0 немає інших потрібних нам функцій.
* **PB4/PB5** — канали CH1/CH2 **одного** таймера TIM3 (AF1): обидва серво 50 Гц, тож спільні
  PSC/ARR не є обмеженням (§5), і один таймер звільняє TIM1/TIM14/TIM16/TIM17.
* **PA8** — вільний GPIO з EXTI8 (лінія 4..15 → один вектор `EXTI4_15`). B1 на PC13
  залишається вільною як резервна кнопка. Рішення «натиснуто» приймає debounce за стабільністю
  рівня (50 мс, опитування 1 кГц у SysTick); EXTI на обидва фронти лише рахує сирі фронти брязкоту
  (журнал проблем, П-12).
* **PB3 (MARK)** — вільний пін на Arduino-роз'ємі, зручно чіпляти щуп; не має бортових функцій
  на Cortex-M0+ (на F4 PB3 — SWO, там треба було б обрати інший). У ЛР3 — імпульс «реакція на кнопку».
* **PA9 / PA10 / PA15 (PROBE0..2, ЛР3)** — службові GPIO для вимірювань логічним аналізатором
  (методичка ЛР3 §5.3). Обрано серед вільних пінів Arduino-роз'єму (D8/D2/D7), що не мають бортових
  функцій і не потрібні жодному інтерфейсу продукту; PA9/PA10 раніше залишались у резерві «під EXTI/таймери»
  (див. вище) — резерв використано саме так. Запис у BSRR — один такт, тож сама «мітка» не спотворює
  вимірюваний час.

**Запас по 3V3.** Пік ≈ 140 мА; LDO 3V3 на Nucleo-64 розрахований на сотні мА (звірити номінал за
UM2953, розділ «Power supply»). Запас достатній, але біля microSD бажано 10 мкФ + 100 нФ: пік
струму запису короткий і різкий.

**Серво — окреме джерело 5 В ≥ 2 А** (UBEC / адаптер), бо: (1) stall-струм двох SG90 (~1.3 А)
більший, ніж USB ST-LINK віддає на 5V Nucleo (≤ 500 мА на весь стенд); (2) пускові кидки

**Земля джерела серво з'єднується з GND Nucleo** — інакше PWM-сигнал не має опорного рівня
(контрольне питання 10). У Wokwi серво живляться від `nucleo:5V` — струм не моделюється.

## 4. Параметри шин і розрахунок від дерева тактування

Дерево (RM, RCC): HSI48 → HSIDIV = 1 → **SYSCLK = 48 МГц** → AHB /1 → **HCLK = 48 МГц** →
APB /1 → **PCLK = 48 МГц**. Таймери на APB з дільником 1 тактуються від PCLK ×1 = 48 МГц.
I2C1 і USART2 тактуються від PCLK (RCC_CCIPR: I2C1SEL = PCLK).

| Шина | Параметри | Розрахунок | Результат | Виміряно (Wokwi, ЛР1) |
|---|---|---|---|---|
| **I2C1** | Standard-mode, 7-біт, analog filter on, digital filter 0 | TIMINGR = `0x20303E5D`: PRESC = 2 → t<sub>PRESC</sub> = 3/48 МГц = 62.5 нс; SCLL = 93 → t<sub>LOW</sub> = 94·62.5 = **5.875 мкс** (≥ 4.7 мкс Sm); SCLH = 62 → t<sub>HIGH</sub> = 63·62.5 = **3.94 мкс** (≥ 4.0 мкс з урахуванням t<sub>SYNC</sub> ≈ 2–3 такти I2CCLK); SCLDEL = 3 → t<sub>SU;DAT</sub> = 250 нс (≥ 250 нс Sm); SDADEL = 0 | f<sub>SCL</sub> ≈ 1 / (5.875 + 3.94 + ~0.15) мкс ≈ **100 кГц** | 100.0 кГц, але 5.0/5.0 мкс (Wokwi ідеалізує, §аналіз) |
| **SPI1** | Master, mode 0 (CPOL = 0, CPHA = 0), MSB first, 8 біт, NSS soft | BR = /128 → 48 МГц / 128 = **375 кГц** (SD init ≤ 400 кГц, SD §6.4.1); після init BR = /8 → **6 МГц** (SD ≤ 25 МГц; запас під макетку) | 375 кГц / 6 МГц | 373.8 кГц (період 2.675 мкс) |
| **USART2** | 115200 8N1, oversampling 16 | BRR = 48·10⁶ / 115200 = 416.67 → **417** → 115 108 біт/с, похибка **−0.08 %** (допуск ±2 %) | 115108 біт/с | 8.68 мкс/біт (розкодовано без помилок) |
| **TIM3** | PWM mode 1, up-counter, ARR preload | PSC = 47 → 48 МГц / 48 = **1 МГц** (1 тік = 1 мкс); ARR = 19 999 → 20 000 мкс = **50 Гц**; CCR = ширина в мкс (500…2500) | 50 Гц, роздільність 1 мкс = 0.09° | 1500.0 мкс / 20 000.0 мкс |
| **ADC1** | 12 біт, sync PCLK/2, sampling 39.5 циклів | f<sub>ADC</sub> = 48 / 2 = 24 МГц; t<sub>CONV</sub> = (39.5 + 12.5) / 24 МГц = **2.17 мкс** | ≤ 3 мкс на відлік | MARK-імпульс — див. `docs/captures/analysis.md` |

**Чому I²C 100 кГц, а не 400 кГц.** Бюджет шини при 200 Гц опитування IMU (FR-01): одне
читання 14 байтів = 2 транзакції ≈ (1+1)+(1+14) байтів ×9 біт + START/STOP ≈ 160 тактів =
1.6 мс при 100 кГц → **32 % шини**. Повне оновлення OLED (1024 байти) — 93 мс. Для ЛР2 (bring-up)
лишаємо перевірений у ЛР1 Sm; для ЛР3 (200 Гц + OLED 5 Гц) Fm уже порахований:
TIMINGR = `0x10311121` (PRESC = 1 → 41.7 нс; SCLL = 33 → t<sub>LOW</sub> = 1.42 мкс ≥ 1.3; SCLH = 17 →
t<sub>HIGH</sub> = 0.75 мкс ≥ 0.6; SCLDEL = 3 → 167 нс ≥ 100; SDADEL = 1), макрос
`BOARD_I2C_TIMING_400K` у `board.h`. Обидва пристрої підтримують Fm (PS §9.3, SSD §13).

**Pull-up на I²C (контрольне питання 3).** GY-521: 4.7 кОм, модуль OLED: 4.7 кОм (типово) → паралельно
2.35 кОм (+ ~40 кОм внутрішнього МК ≈ **2.2 кОм**). Обмеження UM10204 §7.1:
R<sub>min</sub> = (V<sub>DD</sub> − V<sub>OL</sub>) / I<sub>OL</sub> = (3.3 − 0.4) / 3 мА = **0.97 кОм**;
R<sub>max</sub> = t<sub>r</sub> / (0.8473 · C<sub>b</sub>) = 1000 нс / (0.8473 · 50 пФ) = **23.6 кОм** (Sm),
300 нс → **7.1 кОм** (Fm). 2.2 кОм всередині обох діапазонів; струм стоку 1.3 мА.
Кожен новий модуль з власними pull-up зменшує еквівалентний опір — при 4–5 модулях
можна вийти за I<sub>OL</sub> = 3 мА, тоді зайві резистори випаюють.

### 5.1. Камера (OV7670) — чому її немає і що було б на залізі

У Wokwi камери немає, і PRD (Форма B) її не містить. Аналіз сумісності на випадок Форми A:

* **У STM32C031 немає DCMI.** Захоплення GPIO вимагає 8 ліній даних на **одному порту поспіль**
  (читання IDR одним словом), + PCLK, HREF, VSYNC (EXTI) + XCLK 8–24 МГц від MCO.
* MCO на C031 — **PA8** (AF0) або PA9; PA8 зайнятий кнопкою MODE → кнопку довелося б перенести на PC13 (B1).
* Ні PA0..PA7 (ADC, SCK, VCP, LD4, MISO/MOSI), ні PB0..PB7 (CS#, MARK, серво) не вільні цілком —
  розкладка ЛР2 **несумісна** з камерою без повного переведення пінів.
* 12 КБ RAM не вміщують навіть QQVGA RGB565 (160·120·2 = 38.4 КБ) — тільки потокова обробка рядків.
* SCCB камери (адреса 0x21) можна посадити на I2C1 поруч з MPU/OLED, але HAL трактує «don't care»
  9-й біт SCCB як NACK → `HAL_ERROR` (контрольне питання 4).
* На F446 (LQFP64) DCMI займає, зокрема, PB6/PB7 (D5/VSYNC) і PB8/PB9 (D6/D7) як одну з
  альтернатив — тоді I²C треба переносити на I2C2/I2C3 (перевірити за DS10693 табл. AF).

Що з цього не перевіряється в симуляторі: усе, крім пін-конфліктів, — таймінги PCLK, живлення камери,
швидкість GPIO-захоплення.

## 7. Інструкція з підключення (для людини, яка не збирала стенд)

Перевірка: за цим розділом стенд має зібрати учасник, що не брав участі в монтажі ЛР2.

1. **Без живлення.** Від'єднати USB від Nucleo.
2. **Шини живлення макетки:** червону шину → `3V3` Nucleo, синю → `GND`. Окремо: блок 5 В ≥ 2 А,
   його `GND` → синя шина (спільна земля!), `+5V` — тільки на серво.
3. **GY-521 (MPU-6050):** VCC → 3V3, GND → GND, SCL → **D15 (PB8)**, SDA → **D14 (PB9)**. AD0 не чіпати (= 0x68).
4. **OLED SSD1306:** VCC → 3V3 (не 5 В — тоді pull-up потягнуть I²C до 5 В), GND, SCL → D15, SDA → D14
   (паралельно з MPU). Перемичка адреси — 0x3C.
5. **microSD-модуль (без 5 В-регулятора/шифтера або з ним — живити від 3V3):** SCK → **A1 (PA1)**, DO → **D12 (PA6)**,
   DI → **D11 (PA7)**, CS → **D10 (PB0)**, VCC → 3V3, GND. Зовнішній 10 кОм CS → 3V3. Конденсатор 10 мкФ біля модуля.
6. **Потенціометр:** крайні виводи → 3V3 і GND, середній → **A0 (PA0)**.
7. **Кнопка MODE:** один вивід → **PA8** (morpho CN10, ⚠ звірити номер), другий → GND. Резистор не потрібен (внутрішній pull-up).
8. **Серво:** коричневий → GND, червоний → +5 В **зовнішнього** блока, помаранчевий: pan → **PB4**, tilt → **PB5**.
9. **Логічний аналізатор:** GND аналізатора → GND стенда (обов'язково першим), канали — за профілем `bus` (§6).
10. **Перевірка мультиметром до USB:** опір 3V3–GND > 1 кОм (немає КЗ); SCL/SDA–3V3 ≈ 2.2–2.4 кОм (pull-up є, не подвоєні до < 1 кОм).
11. Підключити USB, `make flash`, `make monitor` → очікуваний вивід self-test: `ST END pass=6 fail=0`.

У Wokwi кроки 1–10 відповідають `diagram.json` (той самий перелік з'єднань перевіряє `check_pinout.py`).

## 8. Відхилені варіанти

| # | Варіант | Чому відмовились |
|---|---|---|
| 1 | SPI1_SCK на **PA5** (Arduino D13, «як у прикладах») | PA5 = LD4 (UM «LEDs»): LED навантажує лінію і блимає з частотою SCK; heartbeat LED втрачається. Переносимо SCK на PA1 (та сама AF0) |
| 2 | Серво на **TIM1_CH1/CH2 (PA8/PA9)** | TIM1 — advanced-таймер: потрібен MOE у BDTR (інакше виходи мовчать), PA8 потрібен кнопці (і MCO для камери). TIM3 простіший і на PB4/PB5 нічого не займає |
| 3 | По одному таймеру на серво (**TIM16 + TIM17**) | дає незалежні частоти, які не потрібні (обидва 50 Гц), і з'їдає два таймери, що знадобляться для періодичного опитування IMU (200 Гц) і тригера АЦП у ЛР3 |
| 4 | I2C1 на **PB6/PB7** | працює (AF6), але це D1/D0 — Arduino-позиції UART; модулі з Arduino-роз'ємом очікують I²C на D14/D15 |
| 5 | **I²C 400 кГц** вже в ЛР2 | ЛР2 — bring-up: лишили Sm, перевірений записом ЛР1; Fm розраховано (§4) і вмикається одним макросом у ЛР3 |
| 6 | Читання регістрів з **repeated START** (`HAL_I2C_Mem_Read`) за замовчуванням | обидва пристрої це підтримують, але для STM32C0 у Wokwi повторний START не перевіряли; STOP+START доведено записом ЛР1. Repeated START лишено як режим (`cap rs`) — для експерименту і звіту |
| 7 | **W25Q64** замість microSD | у Wokwi його немає; драйвер написано і протестовано на хості для Форми A (`Devices/w25qxx.c`) |
