## 1. I²C (I2C1, PB8/PB9, 100 кГц)

### 1.1. Запис ЛР1: скан + WHO_AM_I

Декодування sigrok-cli (фрагмент, `lr1_bringup_all.txt`):

```
i2c-1: Start / Write / Address write: 68 / ACK / Data write: 75 / ACK / Stop
i2c-1: Start / Read  / Address read: 68  / ACK / Data read: 68  / NACK / Stop
```

vcdtool (транзакції, тривалість на шині):

```
 685.582 мс  S 76(W)- P        105 мкс   (скан: NACK)
 691.588 мс  S 77(W)- P        105 мкс
 712.582 мс  S 68(W)+ 75+ P    195 мкс   запис вказівника регістра WHO_AM_I
 712.805 мс  S 68(R)+ 68- P    195 мкс   читання: 0x68, NACK від майстра (останній байт)
```

**Зіставлення з datasheet.** RM-MPU §4.32: WHO_AM_I (0x75) містить 0x68. PS §9.3 описує читання
регістра як `S | AD+W | ACK | RA | ACK | Sr | AD+R | ACK | DATA | NACK | P` — з **repeated START**.
На шині видно **STOP + START** замість Sr: прошивка ЛР1 читала двома окремими транзакціями.
MPU-6050 зберігає вказівник регістра між транзакціями, тому відповідь правильна (0x68), і саме
цю схему ЛР2 використовує за замовчуванням (`BOARD_I2C_USE_RESTART 0`); варіант з Sr записується
командою `cap rs` (§1.4). Останній прочитаний байт підтверджено NACK — як вимагає UM10204 §3.1.6.

**Виміряні часові параметри vs розрахунок:**

| Параметр | Розраховано | Виміряно (ЛР1) | Коментар |
|---|---|---|---|
| f<sub>SCL</sub> | ≈ 100 кГц (TIMINGR) | **100.00 кГц** (10.000 мкс) | збіг |
| t<sub>LOW</sub> / t<sub>HIGH</sub> | 5.875 / 3.94 мкс (≈ 60/40 %) | **5.000 / 5.000 мкс** | Wokwi не моделює SCLL/SCLH — генерує ідеальний меандр (аномалія А-3) |
| Транзакція «адреса + 1 байт» | 19 біт + S/P ≈ 195 мкс | **195.0 мкс** | збіг |
| Пауза між записом вказівника і читанням | — | **28.0 мкс** | ≈ 1340 тактів: вихід з `HAL_I2C_Master_Transmit` + вхід у `Receive` |
| Скан, одна відсутня адреса | 9 біт + S/P ≈ 105 мкс | **105.0 мкс на шині, 5.9–6.0 мс між пробами** | HAL чекає таймаут — аномалія А-2 |
| Подія в прошивці → UART | — | 0.81 мс від STOP читання до першого біта рядка `WHO_AM_I = 0x68` | форматування printf + старт передачі |

### 1.2. Ручне декодування (без декодера) — запис вказівника WHO_AM_I

Відлік від START (712 582.225 мс). Біти захоплюються по **фронту SCL↑**, SDA може змінюватися лише при SCL = 0.

| t, мкс | Подія | Біт |
|---:|---|---|

| 10 | SCL ↑, SDA = 1 | A6 |
| 20 | SCL ↑, SDA = 1 | A5 |

| 40 | SCL ↑, SDA = 1 | A3 |
| 50 | SCL ↑, SDA = 0 | A2 |
| 60 | SCL ↑, SDA = 0 | A1 |

### 1.3. Очікування для `i2c_mpu6050_burst.vcd` (команда `cap i2c`)

| # | Очікувано на шині | Пояснення |
|---|---|---|
| 1 | `S 68(W)+ P` | probe MPU (IsDeviceReady) |
| 2 | `S 3C(W)+ P` | probe OLED |
| 3–4 | `S 68(W)+ 75+ P` · `S 68(R)+ 68- P` | WHO_AM_I |
| 5 | `S 68(W)+ 3B+ P` | вказівник на ACCEL_XOUT_H |
| 6 | `S 68(R)+ 00+ 00+ 00+ 00+ 40+ 00+ EF+ 5C+ 00+ 00+ 00+ 00+ 00+ 00- P` | 14 байтів, стан Wokwi за замовчуванням: az = 16384 (1 g), TEMP = −4260 → 24.00 °C; останній байт NACK |

з одного запису й тест `test_capture_vectors_burst_match_uart_log` перевіряє, що драйвер з цих
байтів отримує ті самі числа.

| Виміряти | Розраховано | Виміряно |
|---|---|---|
| тривалість burst-читання | ≈ 1.36 мс | ⏳ |
| ширина вікна MARK | 6 транзакцій ≈ 2.2 мс + паузи HAL | ⏳ |
| затримка MARK↑ → START першої транзакції | десятки мкс | ⏳ |

### 2.1. Запис ЛР1: 80 тактів ініціалізації

```
719.040 мс  CS# low 327.5 мкс   MOSI: FF FF FF FF FF FF FF FF FF FF
```

| Параметр | Розраховано | Виміряно | Коментар |
|---|---|---|---|
| f<sub>SCK</sub> | 48 МГц / 128 = 375 кГц | **373.8 кГц** (2.675 мкс) | крок міток Wokwi 25 нс → округлення |
| такти | 80 | **80** фронтів ↑ | |
| період байта | 8 × 2.667 = 21.3 мкс | **23.35 мкс** | ≈ 2 мкс між байтами — опитування TXE/RXNE у `HAL_SPI_Transmit` |
| CS#↓ → перший SCK | — | **21.98 мкс** | `HAL_GPIO_WritePin` → вхід у HAL_SPI |
| останній SCK → CS#↑ | — | **75.3 мкс** | HAL чекає BSY/FIFO-порожній перед поверненням |
| CPOL | 0 | SCK у спокої = 0 | mode 0 підтверджено |

Зауваження для звіту: у ЛР1 80 тактів подавалися при **CS# = 0**, а SD Spec 6.4.1 вимагає ≥74 тактів

`test_init_sequence_order_and_cs_framing`).

### 2.2. Очікування для `spi_sd_init-read0.vcd` (`cap spi`) — SD Spec розд. 7

| Кадр | MOSI (очікувано, CRC пораховано `sd_crc7`, тест `test_crc7_known_frames`) | MISO (очікувано) |
|---|---|---|
| 80 тактів, CS# = 1 | `FF ×10` | — |
| CMD0 | `40 00 00 00 00 95` | R1 = `01` (idle) |
| CMD8 | `48 00 00 01 AA 87` | R7 = `01 00 00 01 AA` (echo 0xAA) |
| CMD55 | `77 00 00 00 00 65` | `01` |
| ACMD41 (HCS) | `69 40 00 00 00 77` | `01` … потім `00` |
| CMD58 | `7A 00 00 00 00 FD` | `00` + OCR, біт CCS (30) = 1 → SDHC |
| CMD17 блок 0 | `51 00 00 00 00 55` | `00`, …, токен `FE`, 512 байтів, CRC; байти 510/511 = `55 AA` (FAT-образ Wokwi) |

`spi_sd_write.vcd` (`cap spiw`) — «запис з попередньою командою»: `58 00 00 00 01 7D` (CMD24, блок 1) → R1 `00` →
`FF FE` + 512 байтів + `FF FF` → data response `xxx0 0101` (`05`) → MISO = `00` (busy), поки карта пише →
`FF`. CS# утримується від CMD24 до кінця busy. Аналог для W25Q64 (Форма A) — `06` (WREN) окремим
кадром перед `02 aa aa aa dd…`; послідовність перевіряє `test_page_program_is_preceded_by_write_enable`.

| Виміряти | Розраховано | Виміряно |
|---|---|---|
| f<sub>SCK</sub> під час init | 375 кГц | ⏳ |
| f<sub>SCK</sub> під час CMD17 | 6 МГц (після `set_fast`) | ⏳ |
| кількість ACMD41 до готовності | (друкується `acmd41=`) | ⏳ |

## 4. PWM (TIM3 CH1 PB4)

Запис ЛР1 (226 імпульсів):

| Параметр | Розраховано | Виміряно |
|---|---|---|
| період | ARR+1 = 20 000 мкс | **20 000.0 мкс** |
| ширина (CCR = 1500) | 1500 мкс | **1500.0 мкс** (1499.975–1500.025, крок міток 25 нс) |
| перший імпульс | 1500 мкс | **1507.2 мкс** — аномалія А-6 |

Очікування для `pwm_servo_1000-2000us.vcd` (`cap pwm`, профіль `pwm`): PWM_PAN — 5 імпульсів по
**1000 мкс**, потім 5 по **2000 мкс**, далі знову 1500; PWM_TILT — **1250 мкс**. Кут:
1000 мкс → 45°, 2000 мкс → 135° (`servo_us_to_cdeg`). Зміна ширини застосовується **з наступного
періоду** (CCR preload, OCxPE = 1) — затримка MARK↑ → перший імпульс нової ширини ≤ 20 мс,
що й пояснює вимогу FR-03 (латентність ≤ 50 мс) з запасом. ⏳ виміряти.

## 5. ADC — момент і період вимірювання

Цифрового трафіку немає, тому прошивка (`cap adc`) піднімає **MARK** рівно на час
`HAL_ADC_Start → PollForConversion → GetValue` і робить це 20 разів з кроком 5 мс.
На записі (профіль `pwm`, канал MARK) очікується 20 імпульсів: **період 5.000 мс**,
ширина ≈ t<sub>CONV</sub> 2.17 мкс + накладні HAL (≈ 10–30 мкс). ⏳ виміряти.

## 6. SCCB (камера) і паралельна шина камери

Не застосовно у Формі B: у Wokwi немає OV7670, у PRD камери немає. Що і як перевіряли б на залізі —
`docs/pinout.md` §5.1. Для запису паралельної шини (PCLK до 24 МГц) 8-канального FX2-аналізатора
(24 МГц максимум) **не вистачає**: потрібно ≥ 4× f<sub>PCLK</sub>. Варіанти — знизити XCLK/PCLK
(прескалер камери CLKRC) до 1–2 МГц на час запису або записувати лише VSYNC/HREF (кадр/рядок) без
пікселів.

## 7. Аномалії

| # | Що видно | Root cause | Наслідок / дія |
|---|---|---|---|
| **А-1** | Наївний декодер (перша версія `vcd_i2c`) показував `STOP START` посеред байта | Wokwi пише кілька змін SDA з **однаковою міткою часу** (напр. `SDA 1, SCL 0, SDA 0` в одну наносекунду при відпусканні ACK). Якщо обробляти події по одній, виникає «глітч» нульової тривалості при SCL = 1 | `vcdtool.snapshots()` згортає події однієї мітки; синтетичний тест `test_i2c_decode_with_glitches` відтворює саме такі глітчі. sigrok-cli обробляє коректно |
| **А-2** | Відсутня адреса займає **105 мкс** на шині, а наступна проба стартує через **5.9–6.0 мс** | Розбіжність «HAL ↔ шина»: після NACK у режимі AUTOEND `HAL_I2C_IsDeviceReady` чекає прапорець STOPF; у Wokwi він, найімовірніше, не встановлюється після NACK — HAL вичікує повний `Timeout = 5 мс` і повертає `HAL_ERROR` з `ErrorCode = TIMEOUT`, а не `AF` | Скан 112 адрес триває ≈ 0.67 с замість 12 мс. Тому `probe()` у `bus_i2c_stm32.c` трактує будь-яку помилку IsDeviceReady як «немає ACK», а не «таймаут». Перевірка гіпотези: команда `scan` друкує `SCAN ms=` — ≈ 670 у Wokwi, ≈ 15 на залізі. ⏳ |
| **А-3** | SCL 5.0/5.0 мкс замість 5.875/3.94 мкс | Wokwi не моделює поля SCLL/SCLH TIMINGR — лише частоту | Розрахунок t<sub>LOW</sub> ≥ 4.7 мкс у симуляторі не перевіряється; на залізі — лише реальним аналізатором |
| **А-4** | CS# = 0 перші 650 мкс після старту (до `MX_GPIO_Init`) | Після скидання PB0 — вхід без підтяжки; Wokwi показує «0», на залізі — плаваючий рівень | SD може сприйняти шум на SCK як такти під CS#. Рішення на залізі — зовнішній 10 кОм CS# → 3V3 (`pinout.md` §1, §7) |
| **А-5** | Перший «символ» UART на 1.299 мс — `�` | До ініціалізації USART2 лінія TX = 0 (вхід), при перемиканні в AF стає 1; фронт 0→1 при старті і раптова одиниця декодуються як обірваний кадр | Безпечно; на залізі ST-LINK VCP може показати сміттєвий байт на старті — перший рядок лога починаємо з `\r\n` |
| **А-6** | Перший імпульс PWM 1507.2 мкс | `HAL_TIM_PWM_Start` вмикає вихід (CC1E), і лише після цього лічильник (CEN): ≈ 7 мкс HAL-коду, протягом яких вихід уже «1», а лічильник стоїть | Неістотно для серво (±0.6°) |
| **А-8** | Перший прогін ЛР2: двобайтний запис у MPU-6050 закінчився TIMEOUT, наступна проба OLED — BUSY (`lr2_run1_serial.log`) | `HAL_I2C_Master_Transmit` передзавантажує TXDR до START; емулятор не дає TXIS для 2-го байта; периферія лишається з BUSY | регістровий запис по TXIS + скид PE після збою (журнал П-11). ⏳ записати `cap i2c` з `i2cmode 0` і `1` — порівняння на шині покаже, де саме зупиняється транзакція |
| **А-7** (свідома) | `cap nack`: `S 69(W)- P` | Пристрою з AD0 = 1 немає | Очікується `CAP nack addr=0x69 result=NACK` — драйвер повертає `ST_ENACK`, бо `HAL_I2C_GetError` містить AF (навіть якщо разом з TIMEOUT, А-2). ⏳ записати |

Детальніше про виправлення — журнал проблем у `docs/lab2-report.md`.

## 8. Записи перших прогонів ЛР2: зависання запису I²C (П-11, А-8)

Три записи, зроблені на трьох ревізіях драйвера шини (`lr2_run1` — HAL з передзавантаженням TXDR;
`lr2_run2` — запис по TXIS; `lr2_run3` — по TXIS + автоматичні запасні режими).

### 8.1. Що на шині

```
run1  49.011 мс  S 68(W)+ 6B+            ← другий байт (01) так і не пішов; STOP немає
                 SCL = 0 до кінця запису (5.8 с): майстер «розтягує» такт, чекаючи TXDR
run2  56.035 мс  S 68(W)+ 6B+ … (28 мс SCL=0) … Sr 3C(W)+ P   ← скид PE, наступний START виглядає як Sr
      84.349 мс  S 3C(W)+ 00+ AE+ D5+ 80+ … A6+ AF+ P            ← ініціалізація OLED, 27 байтів — УСПІШНО
      86.885 мс  S 3C(W)+ 00+            ← вікно OLED (7 байтів) — те саме зависання після 1-го байта
run3  56.055 мс  S 68(W)+ 6B+ Sr 68(W)+ 6B+ Sr 68(W)+ 6B+ Sr 3C(W)+ P   ← три режими — однаково
```

Рядок діагностики прошивки в момент зависання (run3):
`I2CDIAG … addr=0x68 … isr=0x00008003 cr2=0x020220D0` → ISR: BUSY=1, TXIS=1, TXE=1, **TCR=0**;
CR2: SADD=0xD0, NBYTES=2, AUTOEND=1.

### 8.2. Розбір

**Ключова відмінність — пауза SCL між байтами:**

| Транзакція | Пауза після адреси | Паузи між байтами | Результат |
|---|---|---|---|
| ініціалізація OLED (27 байтів) | 6.5 мкс | 7.25–7.75 мкс після **кожного** байта | ✅ |
| `68 ← 6B 01` | **0** | — (зависання після 1-го) | ❌ |
| вікно OLED `00 21 …` | **0** | — (зависання після 1-го) | ❌ |

* Пауза ≈ 7 мкс після кожного байта означає, що емулятор **не буферизує** TXDR подвійно: TXIS для
  наступного байта з'являється лише після повного завершення попереднього, і майстер тримає SCL,
  поки прошивка не запише TXDR (≈ 340 тактів CPU — опитування ISR).
* У невдалих транзакціях паузи після адреси немає: перший байт уже лежав у TXDR **під час** фази адреси.
  Отже TXIS на старті був «застарілим» (= 1 до того, як периферії справді потрібні дані). Прошивка,
  що орієнтується лише на TXIS, одразу ж записала й **другий** байт — він загубився (TXDR ще зайнятий).
  Емулятор передав `6B`, чекає байт №2 (TXIS = 1, SCL = 0), а прошивка, вважаючи, що все записано,
  чекає STOPF — **взаємне очікування** до таймауту.
* Режим 2 (`HAL_I2C_Mem_Write`) після байта-адреси чекає TCR (RELOAD), а емулятор виставляє TXIS
  замість TCR (ISR = …8003, біт TCR = 0) — у Wokwi цей режим не працює взагалі.
* **«HAL ↔ шина»:** HAL повертає `HAL_ERROR`/TIMEOUT, на шині — валідна транзакція з ACK на кожен байт
  і жодної помилки протоколу. Без запису аналізатора це виглядало б як «MPU не відповідає».

**Виправлення:** після кожного записаного байта чекати, поки TXIS справді скинеться (≤ 200 мкс за
SysTick), і лише тоді — наступний TXIS; те саме для RXNE при читанні (`bus_i2c_stm32.c`,
`BOARD_I2C_GUARD_US`). На залізі запис TXDR скидає TXIS миттєво — поведінка не змінюється.
⏳ Підтвердити записом: у новій прошивці після адреси і кожного байта має з'явитися пауза SCL, а
транзакція `S 68(W)+ 6B+ 01+ P` — завершитися STOP.
